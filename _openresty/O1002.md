---
layout: pitfall
title: "Blocking the event loop"
permalink: /o/O1002/
description: >-
  Nginx and OpenResty run on an event-driven model: any blocking operation in
  Lua stalls the whole worker process, not just the current request. Using the
  standard file I/O (`io.open()`), calling `os.execute()`, or running heavy
  synchronous work inside a request handler blocks every other request handled
  by that worker.
platform:
  - OpenResty
runtime:
  - LuaJIT
---

```lua
-- handler.lua
local f = io.open("/var/log/app.log", "r")   -- blocking file I/O
local content = f:read("*a")
f:close()

os.execute("sleep 1")                        -- blocks the worker for a second
```

Each of these pauses the whole worker: concurrent requests queue up and
latency spikes. Use only non-blocking OpenResty APIs instead:

```lua
-- handler.lua
-- Cosocket for network I/O (HTTP/MySQL/Redis via lua-resty-*):
local sock = ngx.socket.tcp()
sock:settimeout(1000)
sock:connect("127.0.0.1", 6379)
sock:send("PING\r\n")

-- Non-blocking subrequest:
local res = ngx.location.capture("/api/internal")

-- Defer background work outside the request:
ngx.timer.at(0, function()
  -- runs after the handler returns
end)
```

Read files through an internal location served by `ngx.location.capture()`,
or use `lua_shared_dict`/`resty.core` facilities; never do plain synchronous
I/O in a request handler.
