---
layout: pitfall
title: "Lua string patterns are slower and weaker than ngx.re.*"
permalink: /o/O1004/
description: >-
  `string.find`, `string.match` and `string.gsub` use Lua patterns, not PCRE.
  They are compiled on every call, the result is not cached and LuaJIT cannot
  JIT-compile them, so a pattern in a hot handler is both slow and limited.
  Prefer `ngx.re.*` for anything more than a literal search.
platform:
  - OpenResty
runtime:
  - LuaJIT
---

```lua
-- handler.lua
local s = "order 12345 paid"

-- Lua pattern: recompiled on every call, never JIT-compiled,
-- and it cannot express PCRE features such as anchors on a class.
local id = string.match(s, "%d+")   -- "12345"
```

Lua's pattern syntax (`%d`, `%a`, `%s`, ...) is not PCRE, and the matching
engine is a backtracking interpreter that LuaJIT's JIT compiler cannot trace.
A pattern that runs on every request is re-parsed each time; there is no
compiled-pattern cache analogous to the one in `ngx.re`.

Use the OpenResty regex API instead, which compiles the pattern once and caches
compiled regexes (`lua_regex_cache_max_entries`):

```lua
-- handler.lua
local s = "order 12345 paid"

-- "jo": j enables the PCRE JIT, o compiles once and caches the result
local from, to, err = ngx.re.find(s, "\\d+", "jo")
if from then
  local id = string.sub(s, from, to)   -- "12345"
end
```

For a fixed string with no metacharacters, keep the standard library but use
its plain mode, which skips pattern parsing entirely:

```lua
string.find(s, "order", 1, true)       -- plain = true, no pattern engine
```

In OpenResty, prefer APIs in this order: OpenResty (`ngx.*`) first, then LuaJIT
(`ffi`, `bit`), and only then the standard Lua libraries. See
[L1013]({{ '/p/L1013/' | relative_url }}) for the pattern metacharacters that
must be escaped when a Lua pattern is the right tool.
