---
layout: pitfall
title: "A read-modify-write on ngx.shared.DICT races across workers"
permalink: /o/O1003/
description: >-
  `get` and `set` on an `ngx.shared.DICT` are individually atomic, but a
  `get`-then-`set` sequence is not. Two nginx workers can read the same value
  and both write back the same incremented result, losing an update. Use the
  atomic `incr`/`add` operations or a lock instead.
platform:
  - OpenResty
runtime:
  - LuaJIT
---

```lua
-- Two workers run this handler concurrently.
local dict = ngx.shared.limiter
local hits = dict:get("hits") or 0
-- Another worker can run the same two lines here.
dict:set("hits", hits + 1)   -- one increment is lost
```

Each of `get` and `set` is atomic on its own, but nothing serializes the
pair: both workers may read `hits = 0` and both write back `1`. Use the atomic
counter operations, which take an optional initial value:

```lua
local dict = ngx.shared.limiter
local new, err = dict:incr("hits", 1, 0)   -- atomic, initializes to 0
if not new then
  ngx.log(ngx.ERR, "incr failed: ", err)
end
```

`dict:add("key", value)` is the atomic "set if absent" variant. For compound
updates that cannot be expressed with `incr`, serialize access with
`resty.lock`.
