---
layout: pitfall
title: "cdata objects are unsuitable as table keys"
permalink: /p/L1057/
description: >-
  LuaJIT allows cdata objects to index a table, but a cdata object is treated
  like any other garbage-collected reference: keys are hashed and compared by
  identity, not by value. Two numerically equal cdata objects therefore address
  different slots, and a lookup by value never finds the entry.
runtime:
  - LuaJIT
analyzers:
  - semgrep
---

```lua
local ffi = require("ffi")

local key1 = ffi.new("int64_t", 42)
local key2 = ffi.new("int64_t", 42)

print(key1 == key2)    -- true: 64-bit integers compare by value

local t = {}
t[key1] = "answer"

print(t[key1])         -- answer
print(t[key2])         -- nil: key2 is a different cdata object
```

The same happens with the `1LL` / `1ULL` literals, which are cdata values, not
Lua numbers. Convert the value to an ordinary Lua type before using it as a key:

```lua
t[tonumber(key1)] = "answer"
print(t[tonumber(key2)])   -- answer
```

For keys wider than a Lua number, format the cdata into a string (for example
with `tostring`) and use the string as the key.
