---
layout: pitfall
title: "FFI calls report errors with return codes, not exceptions"
permalink: /p/L1085/
description: >-
  C functions do not raise Lua errors: they signal failure with a return value
  such as `NULL` or `-1` and set `errno`. Ignoring the result hides the failure,
  and `ffi.load` is the exception that raises instead of returning `nil`.
runtime:
  - LuaJIT
---

```lua
local ffi = require("ffi")
ffi.cdef[[
    void *fopen(const char *path, const char *mode);
    char *strerror(int errnum);
]]

local f = ffi.C.fopen("/no/such/file", "r")
-- fopen returned NULL; Lua sees nil and no error is raised.
io.write(ffi.string(ffi.C.strerror(ffi.errno())), "\n")
```

Unlike `io.open`, which returns `nil` plus a message, the raw C call is not
wrapped. Check the documented failure value and read `ffi.errno()` immediately
afterwards, while the error number still belongs to this call:

```lua
local ffi = require("ffi")
ffi.cdef[[
    void *fopen(const char *path, const char *mode);
    char *strerror(int errnum);
    int fclose(void *stream);
]]

local function open(path, mode)
  local f = ffi.C.fopen(path, mode)
  if f == nil then
    error("fopen: " .. ffi.string(ffi.C.strerror(ffi.errno())))
  end
  return ffi.gc(f, ffi.C.fclose)
end
```

Only some functions set `errno`, and it is meaningful only when the function
actually indicated an error. Do not rely on `errno` being zero on success.

`ffi.load` is the opposite case: it raises a Lua error when the library cannot
be loaded, so a missing or optional library must be handled with `pcall`:

```lua
local ffi = require("ffi")

local ok, lib = pcall(ffi.load, "does_not_exist")
if not ok then
  print("library unavailable: " .. lib)
end
```
