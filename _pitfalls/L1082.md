---
layout: pitfall
title: "Implicit FFI callbacks are permanent and limited in number"
permalink: /p/L1082/
description: >-
  Passing a Lua function where a C function pointer is expected creates a
  callback that is anchored against garbage collection and cannot be reclaimed
  until the VM exits. Creating one per call eventually exhausts the 500-1000
  callback slots.
runtime:
  - LuaJIT
---

```lua
local ffi = require("ffi")
ffi.cdef[[ int atexit(void (*func)(void)); ]]

for i = 1, 1000 do
  ffi.C.atexit(function() end)   -- a new permanent callback on every iteration
end
-- Eventually raises "too many callbacks", and none of them can be freed.
```

An implicit conversion from a Lua function to a C function pointer creates a
callback and anchors the associated Lua closure. Its lifetime cannot be
inferred, because the C side may store the pointer, so LuaJIT never frees it.
Callbacks are a scarce resource: only about 500-1000 can exist at once,
depending on the architecture.

When the C API does not retain the pointer, create the callback explicitly,
keep the cdata object and free it when done:

```lua
local ffi = require("ffi")
ffi.cdef[[ int atexit(void (*func)(void)); ]]

local cb = ffi.cast("void (*)(void)", function() end)
ffi.C.atexit(cb)
-- ...
cb:free()   -- unanchor the Lua function and release the callback slot
```

`cb:set(func)` replaces the Lua function without consuming a new slot, which is
useful for a handler that is registered once but must change behaviour. Also
prefer pull-style APIs over push-style ones that call back into Lua repeatedly:
callbacks are slow, and the C-to-Lua transition can hit the JIT "bad callback"
panic described in [L1066]({{ '/p/L1066/' | relative_url }}).
