title: "Parsing the cdecl on every ffi.new() is slow on a hot path"
permalink: /p/L1084/
description: >-
  `ffi.new("int", ...)` parses the C declaration string on every call. In a hot
  loop this repeated parsing dominates the cost, and caching function cdata
  instead of the namespace defeats JIT specialization.
runtime:
  - LuaJIT
---

```lua
local ffi = require("ffi")

for i = 1, 1e7 do
  local v = ffi.new("int", i)   -- the string "int" is parsed every iteration
end
```

The declaration is a Lua string, so LuaJIT has to look it up in the type cache
on each call. Parse it once and reuse the resulting ctype object as a
constructor:

```lua
local ffi = require("ffi")
local int_t = ffi.typeof("int")   -- parsed once

for i = 1, 1e7 do
  local v = int_t(i)
end
```

Two related habits from the FFI semantics page:

- Cache the namespace, not the function. The JIT specializes to the identity of
  the namespace and the indexing string, so `ffi.C.strlen` is already turned
  into a constant. Storing it in a local is counter-productive, while
  `local C = ffi.C` is useful.
- Pass an explicit length to `ffi.string` when it is known: avoiding the
  `strlen` scan makes the conversion faster.

Anonymous structs are another repeated-parse trap: each `ffi.new("struct { ... }")`
with an inline anonymous declaration creates a new and distinct ctype. Declare a
named struct or create the ctype once with `ffi.typeof`.
