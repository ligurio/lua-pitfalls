---
layout: pitfall
title: "ffi.gc keeps its finalizer after a manual free"
permalink: /p/L1078/
description: >-
  `ffi.gc` attaches a finalizer to a cdata object and returns the object
  unchanged. If the resource is freed explicitly but the finalizer is left in
  place, the garbage collector calls it again later and frees the memory a
  second time.
runtime:
  - LuaJIT
---

```lua
local ffi = require("ffi")
ffi.cdef[[ void *malloc(size_t size); void free(void *ptr); ]]

local p = ffi.gc(ffi.C.malloc(8), ffi.C.free)
-- ...
ffi.C.free(p)     -- freed explicitly
p = nil
-- The finalizer is still attached: the next GC cycle calls ffi.C.free(p) again.
-- If the allocator already reused that block, unrelated memory is corrupted.
```

The finalizer is a property of the cdata object, not of the address, so it
survives an early `ffi.C.free`. `ffi.gc` also returns the same object and can be
called again, replacing the previous finalizer rather than adding a new one.

Detach the finalizer before freeing the resource by hand:

```lua
local ffi = require("ffi")
ffi.cdef[[ void *malloc(size_t size); void free(void *ptr); ]]

local p = ffi.gc(ffi.C.malloc(8), ffi.C.free)
-- ...
ffi.C.free(ffi.gc(p, nil))   -- remove the finalizer, then free once
p = nil
```

Never associate the same address with two finalizers and do not create a second
`ffi.gc` wrapper around an already-managed pointer. See
[L1065]({{ '/p/L1065/' | relative_url }}) for the broader lifetime rules.
