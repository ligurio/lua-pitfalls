---
layout: pitfall
title: "Do not change the current Lua context outside lua_yield"
permalink: /p/L1091/
description: >-
  The Lua C API keeps the current thread in the interpreter state. Swapping the
  active lua_State by hand, outside the controlled paths of lua_yield and
  lua_resume, leaves the interpreter and the running C code with different ideas
  about which thread is current and corrupts the stack.
runtime:
  - Lua 5.1
  - LuaJIT
---

```c
/* A C function entered from Lua must not replace the active state itself. */
static int bad_switch(lua_State *L)
{
    lua_State *other = get_other_state();
    /* Wrong: the interpreter still considers L current, but the code that
       follows now operates on 'other'. The stacks no longer match. */
    lua_pushinteger(other, 42);
    return 1;
}
```

A context switch is only legal at the points the interpreter expects one:
`lua_yield` (to leave a thread) and `lua_resume` (to enter one), plus the
continuation machinery a host such as Tarantool builds around them. Tarantool
historically restored `cur_L` to work around a bug, and the fix was to restore
it on the exceptional path too, not to switch the active state at arbitrary
points.

Keep the active `lua_State` untouched inside a C function. When a host must run
code in another context, do it through the documented entry points:

```c
static int good_switch(lua_State *L)
{
    /* Let the scheduler resume another thread through the API, and return the
       control flow to the interpreter. */
    lua_yield(L, 0);
    return 0;
}
```
