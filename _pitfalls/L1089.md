---
layout: pitfall
title: "FFI array indexing is not bounds-checked"
permalink: /p/L1089/
description: >-
  A cdata array created with ffi.new() is a raw block of memory. Reading or
  writing at an index outside the declared size is not detected: the access
  corrupts adjacent memory or segfaults, and no Lua error is raised.
runtime:
  - LuaJIT
---

```lua
local ffi = require("ffi")

local ten_ints = ffi.typeof("int[10]")
local a = ffi.new(ten_ints)

a[10] = 1          -- one past the end: no error, corrupts adjacent memory
a[1000000] = 1     -- usually segfaults

local p = ffi.cast("int *", 0)
p[0] = 1           -- null pointer dereference: segfault
```

LuaJIT cannot check these: the array length is not part of the pointer's
runtime state, and the address is just a number, as in C. Keep the size
explicit, never compute an index you have not validated, and prefer Lua tables
when the data does not have to live in C memory.

```lua
local ffi = require("ffi")

local function new_ints(n)
  assert(n > 0, "size must be positive")
  return ffi.new("int[?]", n), n
end

local a, n = new_ints(10)
a[n - 1] = 1       -- last valid index
```

This is one facet of the general rule that the FFI bypasses Lua's memory
safety; see [L1065]({{ '/p/L1065/' | relative_url }}) for the broader lifetime
and ownership rules, and [L1064]({{ '/p/L1064/' | relative_url }}) for the
0-based indexing of FFI arrays.
