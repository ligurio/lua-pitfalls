---
layout: pitfall
title: "FFI must not re-enter the Lua VM (the FFI sandwich)"
permalink: /p/L1066/
description: >-
  LuaJIT supports calling C through the FFI, and it supports C calling Lua
  through the Lua C API, but not the combination `Lua -> FFI -> C -> Lua`: a C
  function entered through the FFI that runs Lua code again produces a
  "sandwich" of stacks that LuaJIT explicitly does not support.
runtime:
  - LuaJIT
analyzers:
  - semgrep
---

```lua
local ffi = require("ffi")

ffi.cdef[[
    // A C function that internally runs Lua code with the Lua C API
    // (lua_call, lua_pcall, lua_resume, ...).
    int run_lua_from_c(lua_State *L);
]]

-- Calling it through the FFI means C will re-enter the Lua VM:
--   Lua -> FFI -> C -> Lua C API -> Lua
-- This sandwich is not supported and can corrupt the stack or crash.
-- ffi.C.run_lua_from_c(L)
```

The FFI call frame stays on the stack while the nested Lua call runs, and
LuaJIT's compiler machinery only understands one kind of entry into the VM at a
time. The same restriction applies to any C code reached through `ffi.C` that
calls back into Lua, including code that triggers Lua callbacks or metamethods.

Keep FFI calls leaf-like with respect to the Lua VM: call functionality that
needs to run Lua through its regular Lua binding (the module's Lua C API
function), not through a raw FFI pointer:

```lua
-- The module enters C from the Lua VM in the supported way and may call
-- Lua callbacks internally without creating an FFI sandwich.
local mymod = require("mymod")
mymod.run_callback(function()
  -- ...
end)
```

If the only access to the C library is through the FFI, restructure the code so
the callback is invoked from Lua rather than from inside the FFI call.
