---
layout: pitfall
title: "FFI bypasses Lua's memory safety"
permalink: /p/L1065/
description: >-
  FFI pointers and cdata are raw memory. Indexing is not bounds-checked, a null
  or invalid pointer is dereferenced without error, and a pointer can outlive
  the object that owns the memory. Mistakes show up as corrupted data or a
  segfault, not as a Lua error.
runtime:
  - LuaJIT
analyzers:
  - semgrep
---

**No bounds checking (spatial safety):**

```lua
local ffi = require("ffi")

local a = ffi.new("int[10]")

a[10] = 1          -- one past the end: no error, corrupts adjacent memory
a[1000000] = 1     -- usually segfaults
```

**Null and invalid pointers:**

```lua
local ffi = require("ffi")

local p = ffi.cast("int *", 0)
p[0] = 1           -- segfault; there is no nil check to catch this
```

**Use after free / dangling pointer (temporal safety):**

```lua
local ffi = require("ffi")
ffi.cdef[[ void *malloc(size_t size); void free(void *ptr); ]]

local p = ffi.C.malloc(4)
ffi.C.free(p)
p[0] = 1           -- writes to freed memory
```

LuaJIT cannot check any of these: the address is just a number. Keep the length
explicit, validate what C returns, and tie the lifetime of allocated memory to
a cdata with `ffi.gc`, keeping the owner reachable while a pointer is in use:

```lua
local ffi = require("ffi")
ffi.cdef[[ void *malloc(size_t size); void free(void *ptr); ]]

local function new_buffer(n)
  local buf = ffi.C.malloc(n)
  if buf == nil then
    error("out of memory")
  end
  return ffi.gc(buf, ffi.C.free)   -- freed when buf becomes garbage
end

local buf = new_buffer(16)
buf[0] = string.byte("x")
```

Use `ffi.gc` to attach a destructor and keep the owning object reachable (for
example, store it next to the pointer) so it is not collected while C still uses
the memory. These bugs are not statically detectable in general; test the C
boundary with sanitizers (AddressSanitizer, Valgrind) as well as Lua-level
tests.
