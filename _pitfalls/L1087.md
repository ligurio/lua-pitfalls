---
layout: pitfall
title: "An out-of-range number passed where an integer is expected"
permalink: /p/L1087/
description: >-
  Several LuaJIT library functions convert their numeric argument to a 32-bit C
  integer. A Lua number that does not fit the 32-bit range is truncated instead
  of raising an error, so the call silently operates on a different value than
  the one written in the source.
runtime:
  - LuaJIT
analyzers:
  - semgrep
---

```lua
-- LuaJIT converts the second argument of string.rep() to a 32-bit integer:
print(string.rep("x", 1024 * 1024 * 1024 * 2))
-- 0 or empty output instead of an out-of-memory error

print(("x"):rep(1024):sub(1024 * 1024 * 1024):len())
-- 0: the length argument wrapped around
```

The reference implementation raises "string too long" or runs out of memory.
LuaJIT goes through `lj_lib_checkint`, which truncates the double to an `int`,
and the wrapped value changes the meaning of the call.

Keep indices and lengths inside the 32-bit range, and validate values that
arrive from outside before passing them to `string.rep`, `string.sub`,
`string.char` and similar functions:

```lua
local function safe_rep(s, n)
  assert(n >= 0 and n <= 2^31 - 1, "length out of range")
  return string.rep(s, n)
end
```

The same truncation is observable in `string.sub`, `string.char` and other
library calls that take an integer argument. See the linked issue for the full
list.
