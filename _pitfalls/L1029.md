---
layout: pitfall
title: "ipairs() never ends if __index always returns a value"
permalink: /p/L1029/
description: >-
  Since Lua 5.3 the iterator behind `ipairs()` resolves a missing element
  through the `__index` metamethod, exactly like an ordinary `t[i]` access.
  If `__index` never returns `nil`, the loop visits 1, 2, 3, ... and never
  terminates. Lua 5.1/5.2 and LuaJIT read the array part directly and stop
  at the first `nil`.
runtime:
  - Lua 5.3
  - Lua 5.4
  - Lua 5.5
---

```lua
-- Lua 5.3+: never terminates (every index is fabricated by __index)
local t = setmetatable({}, {
  __index = function() return 0 end
})

local n = 0
for _ in ipairs(t) do        -- i = 1, 2, 3, ... forever
  n = n + 1
  if n > 1000 then break end -- guard so the demo itself does not hang
end
print(n)                     -- 1001, and still no nil in sight
```

The same loop behaves differently depending on the runtime:

```lua
-- Lua 5.1, Lua 5.2 and LuaJIT:
for _ in ipairs(t) do end    -- stops immediately (t has no elements)

-- Lua 5.3, Lua 5.4 and Lua 5.5:
for _ in ipairs(t) do end    -- never stops
```

Since Lua 5.3 a missing `t[i]` inside the iteration goes through the
`__index` metamethod, just like a plain `t[i]` access, so `ipairs()` can
"fabricate" a value at every index and never find the end of the table.
This is the documented metamethod semantics of an index access, not a Lua
bug - but code that relies on `ipairs()` hitting the first `nil` can hang
(an object whose metatable `__index` supplies numeric values is enough).
Only call `ipairs()` on a plain array, or bound the loop explicitly.

If you need the raw array part, ignoring metamethods:

```lua
local function ipairs_raw(t)
  local i = 0
  return function()
    i = i + 1
    local v = rawget(t, i)
    if v ~= nil then return i, v end
  end
end

for _ in ipairs_raw(t) do end   -- terminates, visits nothing
```
