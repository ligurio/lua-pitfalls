---
layout: pitfall
title: "Lua numbers are silently truncated when written to C integers"
permalink: /p/L1081/
description: >-
  Converting a Lua number to an integer C type narrows or truncates it without
  an error: a fractional part is dropped and an out-of-range value wraps or is
  left architecture-specific. The stored value differs from the one in the
  script.
runtime:
  - LuaJIT
---

```lua
local ffi = require("ffi")

local b = ffi.new("uint8_t", 300)
print(b)                     -- 44   (300 mod 256)

local i = ffi.new("int", 3.9)
print(i)                     -- 3    (truncated towards zero)

local neg = ffi.new("uint32_t", -1)
print(neg)                   -- 4294967295
```

The FFI follows the C conversion rules, so unlike Lua arithmetic there is no
overflow check and no error. A value whose fractional part matters is rounded
down; a value outside the target range wraps around, and for values outside the
range the rules still define, the result is architecture-specific.

Validate and convert explicitly when the values come from users, files or the
network, and clamp to the intended range before writing:

```lua
local ffi = require("ffi")

local function to_uint8(n)
  assert(n >= 0 and n <= 255 and n == math.floor(n), "not a uint8: " .. n)
  return ffi.new("uint8_t", n)
end

local b = to_uint8(300)      -- raises instead of silently storing 44
```

The same narrowing happens for struct fields and array elements assigned a Lua
number. Be explicit about the target type, and remember that `ffi.new("int")` on
a scalar does *not* make the surrounding Lua arithmetic integer: the value is
converted back to a double on every read.
