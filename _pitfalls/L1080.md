---
layout: pitfall
title: "Vararg C calls do not convert Lua numbers to the declared type"
permalink: /p/L1080/
description: >-
  Arguments passed to the `...` part of a C function use default conversion
  rules, where every Lua number becomes a `double`. A vararg function that
  expects an `int` therefore reads a garbled value, and boxing the number with
  `ffi.new` or `ffi.cast` is required.
runtime:
  - LuaJIT
---

```lua
local ffi = require("ffi")
ffi.cdef[[ int printf(const char *fmt, ...); ]]

local n = 42
ffi.C.printf("value: %d\n", n)                   -- n is passed as a double
-- The callee reads an int from the integer register, which was never set.
```

The FFI cannot know the type expected by a C vararg: the prototype ends in
`...` and carries no per-argument information. Its default rule for the vararg
part is Lua number → `double`, but `printf("%d", ...)` reads an `int`. Pass an
explicitly typed temporary instead, which is one of the few places where boxing a
scalar is appropriate:

```lua
local ffi = require("ffi")
ffi.cdef[[ int printf(const char *fmt, ...); ]]

local n = 42
ffi.C.printf("value: %d\n", ffi.new("int", n))   -- correct: an int is passed
ffi.C.printf("value: %f\n", n)                    -- %f matches the default double
```

The same applies to `ffi.cast("int", n)`. Other default vararg conversions are
usually convenient: a Lua string becomes `const char *`, `nil` becomes `NULL`,
and a `float` cdata is promoted to `double`, matching C's own promotion rules.
Do not box scalars outside of vararg calls: cdata arithmetic on a boxed scalar
is always performed on 64-bit integers and only adds conversion overhead
(see [L1061]({{ '/p/L1061/' | relative_url }}) and
[L1062]({{ '/p/L1062/' | relative_url }})).
