---
layout: pitfall
title: "A blocking C call through the FFI freezes the whole LuaJIT VM"
permalink: /p/L1083/
description: >-
  LuaJIT is single-threaded and cannot preempt a C function. A blocking call
  such as `sleep`, `read` or `recv` entered through the FFI stops every
  coroutine, timer and garbage collection step until it returns.
runtime:
  - LuaJIT
---

```lua
local ffi = require("ffi")
ffi.cdef[[ unsigned int sleep(unsigned int seconds); ]]

local function wait()
  sleep(5)      -- the entire VM is frozen for 5 seconds
end

local co = coroutine.create(function()
  while true do
    coroutine.yield("tick")
  end
end)
-- While wait() runs, co, timers and the GC make no progress.
```

There is no preemption: the C function runs to completion on the only thread,
and coroutines are cooperative anyway. A blocking call in library code is
therefore not just a slow operation, it stalls unrelated work, including the
garbage collector, and defeats any event loop built on coroutines.

Move blocking work off the main thread or use a non-blocking API with a poller:

```lua
local ffi = require("ffi")

-- Sketch: run the blocking work in an OS thread and deliver the result back.
local uv = require("luv")
local work = uv.new_thread(function(seconds)
  ffi.C.sleep(seconds)
end, 5)

-- Or open the descriptor non-blocking and wait with poll/epoll/select
-- instead of calling a blocking read.
```

When a C library only offers blocking entry points, isolate it in a worker
thread or process rather than calling it directly from the event loop.
