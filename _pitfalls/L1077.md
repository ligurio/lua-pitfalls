---
layout: pitfall
title: "A C library namespace must stay reachable while its symbols are used"
permalink: /p/L1077/
description: >-
  `ffi.load` returns a C library namespace that is itself garbage collected. When
  the last reference to the namespace is gone, LuaJIT may release the shared
  library and remove the bound symbols, so function cdata obtained from it
  becomes stale and calling it crashes.
runtime:
  - LuaJIT
---

The namespace is only referenced by a local variable, but a symbol is returned
from the function:

```lua
local ffi = require("ffi")
ffi.cdef[[ uint32_t crc32(uint32_t crc, const void *buf, size_t len); ]]

local function lookup()
  local z = ffi.load("z")   -- only a local reference
  return z.crc32            -- the function cdata outlives the namespace
end

local crc32 = lookup()
collectgarbage()            -- the 'z' namespace may be collected...
print(crc32(0, "abc", 3))   -- ...and the symbol address becomes stale
```

The namespace is a garbage-collected object. Releasing it can remove the shared
library from the process, and every function cdata bound through it is no longer
guaranteed to point at valid code. [L1065]({{ '/p/L1065/' | relative_url }})
describes the same "raw pointer outlives its owner" class of bug.

Keep the namespace reachable for as long as any of its symbols are used, for
example by holding it in an upvalue, a module table or another long-lived
object:

```lua
local ffi = require("ffi")
ffi.cdef[[ uint32_t crc32(uint32_t crc, const void *buf, size_t len); ]]

local z = ffi.load("z")     -- module-level: lives as long as the module

local function mycrc32(s)
  return z.crc32(0, s, #s)
end
```

For the same reason it is unsafe to return symbols from a library without the
namespace that owns them. Note also that `ffi.load` raises on failure instead of
returning `nil`; wrap it in `pcall` if a missing library is expected
(see [L1085]({{ '/p/L1085/' | relative_url }})).
