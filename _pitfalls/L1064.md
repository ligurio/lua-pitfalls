---
layout: pitfall
title: "FFI arrays are 0-based and have no length operator"
permalink: /p/L1064/
description: >-
  C arrays start at index 0, while Lua tables start at 1. Code that follows Lua
  conventions writes one element past the end of an FFI buffer, and cdata arrays
  do not support `#`, so the mistake is not caught. The result is heap or stack
  corruption.
runtime:
  - LuaJIT
---

```lua
local ffi = require("ffi")

local a = ffi.new("int[3]", {10, 20, 30})

print(a[0], a[1], a[2])     -- 10  20  30
print(a[3])                 -- out of bounds: undefined value

-- Lua habit: the "first" element is index 1, and the length is #a.
local sum = 0
for i = 1, #a do            -- #a raises "attempt to get length of 'int [3]'"
  sum = sum + a[i]
end
```

The buffer holds 3 elements at indices `0..2`. Indexing `a[3]` reads past the
end, and writing `a[3] = x` corrupts the memory after the buffer. A larger
mistake, such as `a[1000000] = 1`, usually segfaults.

Track the length separately and use C indexing:

```lua
local ffi = require("ffi")

local n = 3
local a = ffi.new("int[3]", {10, 20, 30})

local sum = 0
for i = 0, n - 1 do
  sum = sum + a[i]
end

-- Number of elements can also be derived from the byte size.
local count = ffi.sizeof(a) / ffi.sizeof("int")   -- 3
```

The `#` operator works for cdata only for some vector types, not for plain
arrays, so never rely on it to bound a loop. See
[L1065]({{ '/p/L1065/' | relative_url }}) for why an out-of-bounds access is not
diagnosed.
