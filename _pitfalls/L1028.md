---
layout: pitfall
title: "math.random() takes only integer arguments"
permalink: /p/L1028/
description: >-
  `math.random(m, n)` takes integer bounds and returns an integer in `[m, n]`.
  Passing floating-point (double) arguments is outside this contract and
  behaves differently per implementation: Lua 5.1 silently truncates the
  bounds to integers, Lua 5.3+ rejects them with "number has no integer
  representation", and LuaJIT computes in floating point, where rounding can
  return a value greater than `n`.
runtime:
  - Lua 5.1
  - Lua 5.2
  - Lua 5.3
  - Lua 5.4
  - Lua 5.5
  - LuaJIT
---

```lua
-- Lua 5.1: silently truncates to integer bounds
print(math.random(-72.3, 42.6))   -- integer in [-72, 42]

-- Lua 5.3+: Runtime error: bad argument #2 to 'random'
--           (number has no integer representation)
print(math.random(-72.3, 42.6))

-- LuaJIT: accepts floats, but may return a value above the upper bound
local a, b = -72.3, 42.6
for _ = 1, 10000000 do
  if math.random(a, b) > b then
    error("Invalid random return!")
  end
end
```

`math.random()` returns an integer in `[m, n]`; only integer arguments are
supported. The implementations differ when doubles are passed: Lua 5.1
truncates them silently, Lua 5.3+ raises "number has no integer
representation", and LuaJIT computes the value in double precision as
`a + r * (b - a)`, where rounding can produce a result just above `b`.

Always pass integer bounds, or convert them first:

```lua
-- Always pass integer bounds:
local a, b = -72, 42
local v = math.random(a, b)
assert(v >= a and v <= b)

-- Or convert floating-point bounds explicitly:
local v = math.random(math.floor(-72.3), math.ceil(42.6))
```

The LuaJIT issue notes that the failure does not reproduce when `a + b` fits
in an integer.
