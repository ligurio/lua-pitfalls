---
layout: pitfall
title: "C strings and Lua strings have different representations"
permalink: /p/L1079/
description: >-
  Lua strings are length-prefixed and may contain embedded NUL bytes, while C
  strings are NUL-terminated and have no length. Converting between them without
  an explicit length silently truncates data or reads past the buffer.
runtime:
  - LuaJIT
---

`ffi.string(ptr)` without a length calls `strlen`, so an embedded zero cuts the
result short, and a buffer that is not NUL-terminated is over-read:

```lua
local ffi = require("ffi")

local s = "a\0b"                          -- a Lua string of length 3
local buf = ffi.new("char[?]", #s, s)     -- copies exactly 3 bytes, no terminator

print(#s)                       -- 3
print(#ffi.string(buf))         -- 1: strlen stopped at the embedded NUL
print(ffi.string(buf, #s))      -- 3: the explicit length is honoured
```

`ffi.string` with an explicit length copies the bytes and is the correct form
when the size is known (for example, a length returned by the C call). It is
also faster, because no scan for the terminator is needed.

`ffi.copy` has a related caveat: the three-argument form
`ffi.copy(dst, str, len)` must not be given a `len` greater than `#str + 1`, and
the two-argument form copies the string *plus* a trailing zero byte:

```lua
local ffi = require("ffi")

local out = ffi.new("char[?]", 8)
ffi.copy(out, "hi")           -- copies "hi\0" (3 bytes)
ffi.copy(out, out, #"hi")     -- copies only the 2 bytes, without a terminator
```

A Lua string passed to a `const char *` parameter is converted to a pointer to
its internal buffer, which is NUL-terminated; this is safe for the duration of
the call, but the pointer must not be stored by C, because the string can be
collected afterwards. Note that wide strings and character literals are not
supported by the FFI parser at all.
