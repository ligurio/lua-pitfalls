title: "The order of pairs() iteration is undefined"
permalink: /p/L1027/
description: >-
  `pairs()` iterates a table in no guaranteed order. The order depends on the
  internal hash/array layout, on how and in what sequence elements were
  inserted, and even on the Lua implementation or version — LuaJIT 2.1 can
  produce different orders across separate VM invocations. Relying on the
  order of `pairs()` is a bug; if you need a deterministic order, sort the
  keys, or use `ipairs()` for the array part, which visits indices `1..#t` in
  order.
runtime:
  - Lua 5.1
  - Lua 5.2
  - Lua 5.3
  - Lua 5.4
  - Lua 5.5
  - LuaJIT
---

```lua
local t = {a = 1, b = 2, c = 3}
local keys = {}
for k in pairs(t) do table.insert(keys, k) end
print(table.concat(keys, ", "))   -- arbitrary: e.g. "a, b, c" or "c, a, b"

local arr = {10, 20, 30}
for k, v in pairs(arr) do         -- pairs() on an array: no ascending order
  print(k, v)                     -- may print 3 30, 1 10, 2 20
end
```

The order of table iteration is explicitly undefined by the Lua language
standard. It differs between implementations and versions, depends on the
order in which elements were inserted, and with LuaJIT 2.1 it can even change
between separate VM invocations (due to improved VM security and string-key
interning).

If a deterministic order matters, iterate the array part with `ipairs()` or
sort the keys first:

```lua
local arr = {10, 20, 30}
for i, v in ipairs(arr) do        -- guaranteed 1, 2, 3
  print(i, v)
end

local t = {b = 2, a = 1, c = 3}   -- arbitrary keys: sort first
local keys = {}
for k in pairs(t) do table.insert(keys, k) end
table.sort(keys)
for _, k in ipairs(keys) do
  print(k, t[k])
end
```

`ipairs()` exists precisely to make two guarantees that `pairs()` does not:
ascending order and coverage of the array part only. See also
[L1005]({{ '/p/L1005/' | relative_url }}) and
[L1004]({{ '/p/L1004/' | relative_url }}).
