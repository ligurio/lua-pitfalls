---
layout: pitfall
title: "Comparing a 64-bit cdata integer with a Lua number"
permalink: /p/L1096/
description: >-
  A Lua number is a double and holds integers exactly only up to 2^53, while a
  LuaJIT int64/uint64 cdata is exact. Converting between them loses precision,
  and comparing the two converts the Lua number to a 64-bit integer, so equality
  can hold for values that are visibly different.
runtime:
  - LuaJIT
---

```lua
local v = 9223372036854775807LL   -- 2^63 - 1, printed as 9223372036854775807LL

local n = tonumber(v)
print(n)          -- 9.2233720368548e+18: the low bits are gone
print(n % 10)     -- 0
print(v % 10)     -- 7LL

print(n == v)     -- true: the comparison converts n back to int64
```

`tonumber` rounds the cdata to the nearest double, and the comparison operators
convert the double back to a 64-bit integer for the cdata comparison, so
`n == v` reports equality even though `n` no longer holds `v`. Values outside
2^53 should stay cdata and never be round-tripped through a Lua number.

Convert only when the value is known to fit a double, and compare like with
like:

```lua
local v = ffi.new("int64_t", 9007199254740992)   -- 2^53, still exact

if tonumber(v) == 9007199254740992 then           -- safe up to 2^53
  print("exact")
end

-- Keep both sides cdata for full 64-bit precision:
local w = ffi.new("int64_t", 9007199254740993)
print(v == w)                                     -- false, exact comparison
```

See [L1061]({{ '/p/L1061/' | relative_url }}) for the precision limit of Lua
numbers and [L1062]({{ '/p/L1062/' | relative_url }}) for why `math.*` rejects
cdata.
